# 流程细则与判定标准

## 阶段划分

| 阶段 | 目的 | 通过标准 | 失败怎么办 |
|---|---|---|---|
| 0 确认 | 问清两件事 | 费用名称、摘要都有明确答复 | 停下来问，不要猜 |
| 1 汇集 | 票、单分离 | 发票数 × 2 ≈ 文件总数（每张发票配一张行程单） | 数量对不上先查是否有其他压缩包 |
| 2 核价 | 金额可信 | 每张都有金额，逐张与文件名一致，合计自洽 | 有 `problems` 必须逐条报给用户 |
| 3 转图 | 图能看清 | 300 DPI，宽高比正常（1.1–1.8） | 比例异常说明页面框设置怪，检查 CropBox |
| 4 排版 | 每页 2 张 | 行高 ≤ 可用高 ÷ 2 | 超了就减小 `--gap` 或 `--box-w` |
| 5 填单 | 五个字段对 | 名称/摘要/分格/大小写/张数 | 表头识别失败说明模板不是这个版式 |
| 6 合并 | 页序正确 | 第 1 页表单，第 2 页起发票 | 表单进了单元格 = 用了 InsertFile |
| 7 校验 | 可打印 | 实测页数 = 1 + ⌈n÷2⌉，逐页 2 张 | 多一页 = 末尾空段没压住 |

## 阶段 0 的沟通方式

用户是普通人，问题越少越好。**只问两个**，其余一律用默认值（见 SKILL.md 的默认值表）。

先跑 Step 1 和 Step 2，拿到「N 张、合计 X 元」这个事实，再问：

> 这批发票共 3 张，合计 123.45 元。两个问题确认一下：
> 1. 费用名称填什么？（比如交通费、差旅费、办公用品）
> 2. 摘要（备注）写什么？建议写成「时间 + 用途」

有了数字，用户更容易判断「这笔钱应该归到哪个科目」。

**不要问明细怎么分行。** 默认合并成 1 行；只有当发票超过 8 张、并且用户主动提到「看不出来是哪些」时，才建议按平台拆。

**要主动提示口径风险。** 如果金额和发票内容明显不匹配（例如报销单写「订阅月费」，附件全是打车票），必须提醒：财务大概率退回。提示一次即可，用户坚持就按用户的来。

## 阶段 1 的细节

打车平台（滴滴、高德等）的导出包通常是「一张发票 + 一张行程单」成对出现，文件名形如：

```
【平台名-金额元-N个行程】某打车电子发票.pdf
【平台名-金额元-N个行程】某打车电子行程单.pdf
```

判定规则：文件名含「行程单」→ 行程单；含「发票」→ 发票；都不含但有同名 XML → 发票。行程单**不进**报销附件（少数单位要求附行程单，此时按用户要求额外合并）。

## 阶段 2 的取数优先级

1. 数电票 XML 的 `TotalTax-includedAmount` —— 最权威，与票面「价税合计（小写）」一致
2. PDF 文本层提取 —— 仅在 XML 缺失时兜底，很多发票内嵌字体，取不到中文
3. 文件名标注金额 —— 只用于校验，绝不作为结果

三者关系：以 1 为准，用 3 校验，2 用来在 1 缺失时救急。

## 阶段 3 的裁剪判据

`03_render.py` 用「与纯白的差异」求内容外接框，四周留 8px 余量。两个保护：

- 外接框为空（整页纯白）→ 不裁
- 外接框面积 < 全图 20% → 判定为异常，不裁

裁完宽高比应在 1.1–1.8。若出现 0.7 之类的竖版比例，说明 PDF 页面框和内容不匹配，需要检查 `MediaBox` / `CropBox`，而不是硬调图片。

## 阶段 4 的排版算术

```
可用宽 = 210 - 2×12 = 186mm
可用高 = 297 - 2×12 = 273mm
行高   = (273 - 间隔×(每页张数-1)) / 每页张数 = (273-8)/2 = 132.5mm
图高上限 = 行高 - 2 = 130.5mm
```

`ROW_HEIGHT_RULE.EXACTLY` + `cantSplit` 一起用：行高固定保证每页正好两行，cantSplit 保证单张发票不会被劈到两页。

## 阶段 7 的验收动作

1. 脚本打印结构信息：表格数、图片数、显式分页数
2. Word 实测页数，与公式比对
3. 导出 PDF，逐页数图片：第 1 页 0 张，其后每页 = per-page
4. **逐页看图**（不能只看总数）：第 1 页查表单错位，中间页查裁切，末页查是否只剩 1 张

末页只有 1 张是正常的（奇数张时），但末页出现 3 张或空页就是排版错了。
